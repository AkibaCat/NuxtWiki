# NuxtWiki Deployment Guide

NuxtWiki uses a **pure static SPA frontend (Nuxt 4) + PHP API** architecture and can be deployed on PHP-capable virtual hosts such as **Kangle (easypanel) / Apache / Nginx**:

- **Frontend**: static build output of Nuxt with `ssr: false` — pure HTML/JS/CSS, the server requires **no Node runtime**.
- **Backend**: PHP API (the `api/` directory, PDO direct DB access), routed via `index.php?r=<controller>.<action>`.
- **Database**: **MySQL** in production, **SQLite** for local development; both schemas are provided and the installation wizard will automatically create the tables.

> This guide is written following a "package locally first, then upload and deploy" flow, and is compatible with common environments such as Kangle / Apache / Nginx / BT Panel (Nginx) (BaoTa).

---

## 1. Environment Requirements

| Component     | Requirement                                                                             |
|---------------|-----------------------------------------------------------------------------------------|
| Server        | Kangle (easypanel) or another Web server that supports PHP                               |
| PHP           | ≥ 8.1, required extensions: `pdo_mysql`, `mbstring`, `fileinfo`<br>Optional extensions: `openssl`, `curl`, `gd`, `zip` |
| MySQL         | 5.7+ / 8.0, charset `utf8mb4` (collation `utf8mb4_unicode_ci`)                        |
| Writable dirs | `api/data/`, `api/uploads/` (the framework writes runtime data and uploaded attachments) |

> Local development uses SQLite (requires `pdo_sqlite`); production uses MySQL.

---

## 2. Site Directory Structure

Place the build output and the API in the **same site root directory** (assume deployment under the domain root path `/`):

```
Site root directory/
├── index.html          ← SPA entry (Nuxt static build output)
├── 200.html            ← SPA fallback
├── 404.html
├── _nuxt/              ← Frontend JS/CSS assets
├── _fonts/             ← Font assets
├── account/  admin/  pages/  recent/  search/
├── register/  login/  settings/       ← Static route shells (generated by nuxt generate)
├── .htaccess           ← Rewrite (SPA fallback) rules
└── api/                ← PHP backend
    ├── index.php       ← API entry point
    ├── install.php     ← Installation wizard
    ├── bootstrap.php
    ├── schema.mysql.sql / schema.sqlite.sql
    ├── seed/           ← Initial page content (welcome.md / grammar-help.md)
    ├── src/            ← Core classes and controllers
    ├── config.php      ← Auto-generated after install (contains DB connection info)
    ├── data/           ← Runtime data (SQLite / backups), must be writable
    └── uploads/        ← Attachment upload directory, must be writable
```

> ⚠️ The frontend accesses resources via **root-path absolute URLs** (`/api/index.php`, `/_nuxt/...`), so this site must be deployed at the **domain root path**. If you need to deploy into a subdirectory (e.g. `example.com/subdir/`), rebuild and configure `app.baseURL` and `NUXT_PUBLIC_API_BASE`.

## 3. Build & Package (run on your local dev machine)

### 3.1 Option One: One-click script (recommended)

The repo provides `build-deploy.sh`, which automatically handles "install dependencies → build frontend → assemble backend → package":

```bash
./build-deploy.sh
```

- Output: `deploy/nuxtwiki-<version>.tar.gz` (the default version is a timestamp; specify `VERSION=1.2.0` to override).
- The archive does **not nest an outer directory** — extracting it yields the site root directory content directly.
- The script **excludes runtime files** at the source: `api/data`, `api/uploads`, `api/config.php` (these are auto-generated at install time).

### 3.2 Option Two: Manual build

```bash
pnpm install
pnpm generate
```

The build output lives in `.output/public/`. Copy **all of its contents** (including `index.html`, `200.html`, `404.html`, `.htaccess`, `_nuxt/`, and the route shells) into the site root directory, then copy the entire `api/` directory to `Site root directory/api/` (be sure to keep `api/seed/`).

> ⚠️ You must use **`nuxt generate`** (SPA mode). It generates `index.html`, `200.html`, `404.html`, and the static route shells; `nuxt build` (the node-server preset) does not generate `index.html` and cannot be used for a pure static deployment.

### 3.3 Fetching the output via CI

After every `git push`, `.github/workflows/ci.yml` automatically builds and uploads the deployment package:

- Repository → **Actions** → select the latest run → **Artifacts** at the bottom → download `nuxtwiki-deploy`.
- Release builds are also available on the repository's **Releases** page: Releases page → the corresponding version tag → **Assets** (source archives plus the bundled deployment package).

### 3.4 Pulling from the gh-pages branch

After the CI build finishes, it also **pushes the output directly to the `gh-pages` branch** (handled by `peaceiris/actions-gh-pages`), so you can deploy by pulling that branch's content directly without building locally:

```bash
git fetch origin gh-pages
git checkout -b gh-pages origin/gh-pages   # first time: create a local branch from the remote one
# or if you already have a local branch: git checkout gh-pages && git pull origin gh-pages
```

- That branch's root directory is the site root content (`index.html`, `api/`, `_nuxt/`, etc.); pull it and upload it to the server's site root.
- Since the `gh-pages` branch is fully rebuilt every time via `force_orphan: true`, **do not** modify it directly and push, or it will be overwritten by the next CI run; keep long-term site-content changes on the `main` branch.
- This branch is typically used for "server deploys by pulling via git" automation scenarios.
- If you only want to download the deployment package, it's easier to use the Artifacts from 3.3 or the **Assets** on the repository's **Releases** page.

## 4. Upload & Deploy

1. Obtain the deployment package `nuxtwiki-<version>.tar.gz` (download it from the **Assets** on the repository's **Releases** page, or use the CI Artifacts from 3.3 / generate it locally with `./build-deploy.sh`), then upload it to the server (FTP / SFTP / panel file manager / `scp`).
2. Extract it in the server's site root directory (`tar -xzf nuxtwiki-<version>.tar.gz`), making sure `index.html`, `api/`, and `.htaccess` land directly under the root.
3. No need to import the schema manually — the installation wizard will automatically create the tables.
4. Ensure `api/`, `api/data/`, and `api/uploads/` are **writable** by the PHP process (see Section 5.5).
5. Open `http://your-domain/api/install.php` in a browser to complete the installation (see Section 5).

## 5. Production Installation & Configuration

### 5.1 Configuring PHP handling (Kangle)

In the easypanel, select a **PHP version (8.1+)** for the site. Kangle automatically handles `.php` requests via FastCGI, so no additional configuration is needed.

Make sure the server's PHP has enabled the `pdo_mysql`, `mbstring`, `fileinfo` extensions (uncomment the corresponding `extension` lines in the server's `php.ini`).

### 5.2 Configuring rewrite rules (SPA fallback)

Create a `.htaccess` file in the site root directory (Kangle supports Apache-style rewriting):

> This file is already included in the `public` directory and the deployment package, so there is no need to create it manually.

```apache
<IfModule mod_rewrite.c>
RewriteEngine On
RewriteBase /

# API requests are handled by PHP (not rewritten)
RewriteCond %{REQUEST_URI} !^/api(/|$)

# Existing files/directories (_nuxt, _fonts, favicon, uploads, etc.) are not rewritten
RewriteCond %{REQUEST_FILENAME} !-f
RewriteCond %{REQUEST_FILENAME} !-d

# All other paths (/page-name, /page-name/edit, /admin, etc., front-end routes) are served by the SPA entry
RewriteRule ^(.*)$ /index.html [L]
</IfModule>
```

Key points:
- `/api/index.php`, `/api/install.php`, `/api/uploads/...` are real files, and `RewriteCond %{REQUEST_FILENAME} !-f` guarantees they are never rewritten;
- the `!^/api` condition intercepts "nonexistent /api paths" to prevent them from being wrongly fallen back to the SPA;
- if the panel requires the rewrite rules to be configured in the control panel, fill in the above `RewriteCond` / `RewriteRule` in the panel's format.
- **Nginx** users should convert the above rules to the equivalent `try_files $uri $uri/ /index.html;` (and make sure requests under `/api` are handed to PHP, not fallen back to the SPA).

### 5.3 Create the MySQL database

```sql
CREATE DATABASE nuxtwiki DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'nuxtwiki'@'localhost' IDENTIFIED BY 'your-strong-password';
GRANT ALL PRIVILEGES ON nuxtwiki.* TO 'nuxtwiki'@'localhost';
FLUSH PRIVILEGES;
```

> No need to import the schema manually — the installation wizard will automatically execute `schema.mysql.sql`.

### 5.4 Run the installation wizard

Open `http://your-domain/api/install.php` in a browser:

1. The **environment check** should all pass (`PDO_MYSQL` must be ✓, each directory writable ✓);
2. Select **MySQL** as the database type, and fill in host / port / database name / user / password;
3. Fill in the site name, homepage page name, and admin account/password;
4. Click "Start Installation".

After installation completes, it automatically generates `api/config.php` (writing the MySQL connection info and creating the tables), creates the admin account, and imports the two initial pages (homepage, grammar help) from `api/seed/`. Finally it returns to the site homepage.

> The initial page content comes from `api/seed/welcome.md` and `api/seed/grammar-help.md` (the site name is injected via the `{{SITE_NAME}}` placeholder). To customize the default content, edit the corresponding `.md` file and reinstall.

### 5.5 Set directory permissions

Make sure the Kangle / PHP process has **write** permission to the following directories:

- `api/data/` — SQLite / backup files
- `api/uploads/` — attachment uploads

On Linux you can run `chown -R <php-user>:<group> api/data api/uploads`, `chmod -R u+w api/data api/uploads`;
on Windows, right-click the directory in File Explorer → Properties → Security and grant the "Modify" permission to the running account.

### 5.6 Verification Tests

- Visit the homepage `http://your-domain/` — it should render normally and show the navigation;
- Visit `http://your-domain/Home` — it should open correctly via the SPA fallback;
- Log in with the admin account, create a page, upload an attachment;
- Visit `http://your-domain/api/index.php?r=admin.stats` (should return 401/403 when not logged in);
- Visit `http://your-domain/api/index.php?r=page.get&tag=HomePage` — it should return the page's JSON data.

## 6. BT Panel (BaoTa) + Nginx Specific Deployment

This section targets the common **BT Panel + Nginx + PHP-FPM + MySQL** environment. If you use Kangle or Apache, follow Section 5 above.

### 6.1 Install the runtime environment

In the BT Panel "Software Store", install:

| Software | Version requirement | Notes                       |
|----------|---------------------|-----------------------------|
| Nginx    | any recent version  | Default BT Panel Web server |
| PHP      | ≥ 8.1               | 8.1 / 8.2 / 8.3 all fine    |
| MySQL    | 5.7+ / 8.0          | charset `utf8mb4`           |

Go to "Websites → PHP settings → Install extensions" and check **`pdo_mysql`, `mbstring`, `fileinfo`** (optional `openssl`, `curl`, `gd`, `zip`).

### 6.2 Add a site and upload the deployment package

1. Generate the deployment package locally: `./build-deploy.sh` (or download from Releases / CI Actions).
2. In BT Panel "Websites → Add site", bind the domain and create the site.
3. Upload `nuxtwiki-<version>.tar.gz` to the server and extract it in the site root `www/wwwroot/<site-name>/`, making sure `index.html`, `api/`, and `_nuxt/` land directly in the root.
4. In BT Panel "Websites → Settings → Website directory", set the **run directory** to the site **root directory** (`/`). The frontend accesses resources via root-path absolute URLs, so it must be served from the root path; for subdirectory deployment, see the note in Section 2 above.

### 6.3 Create the database and run the installation wizard

1. In BT Panel "Database", create a new database with charset `utf8mb4` → collation `utf8mb4_unicode_ci`.
2. Open `http://your-domain/api/install.php`, select **MySQL** as the database type, fill in host / port / database name / user / password, and complete the installation.

### 6.4 Configure Nginx rewrite rules (SPA fallback)

`.htaccess` only applies to Apache. Nginx requires configuring in BT Panel "Websites → Settings → Rewrite rules". The core principle is: **real files and the PHP requests under `/api` should not fall back to the SPA**:

```nginx
location / {
    # Existing real files/directories (_nuxt, _fonts, api/uploads, etc.) are served directly
    if (-e $request_filename) { break; }
    # The remaining front-end routes (/page-name, /page-name/edit, /admin, etc.) fall back to the SPA entry
    rewrite ^(.*)$ /index.html last;
}

# Key: PHP requests under /api are handed to PHP-FPM, preventing them from being fallen back to the SPA by the rewrite above
location ~ ^/api/.+\.php$ {
    include enable-php.conf;
}
```

> Key point: BT Panel enables PHP-FPM parsing via `include enable-php.conf;`, so be sure to keep it; this rule is equivalent in logic to the `RewriteCond !^/api` in the Apache `.htaccess` from Section 5.2.

### 6.5 Directory permissions

Make sure `api/data/` and `api/uploads/` are writable by the PHP-FPM runtime user (usually `www`):

- In BT Panel "Files", select these two directories → right-click "Permissions", set the owner to `www`, and check the write permission;
- Or run in the terminal:

```bash
chown -R www:www api/data api/uploads
chmod -R u+w api/data api/uploads
```

## 7. Troubleshooting

| Symptom                              | Diagnosis |
|--------------------------------------|-----------|
| Visiting `/page-name` returns 404    | No rewrite fallback configured — check that `.htaccess` uploaded correctly and that Kangle has the rewrite module enabled |
| Pages open but data requests fail    | Check whether `/api/index.php` is accessible; whether `config.php`'s MySQL connection is correct; whether `pdo_mysql` is enabled |
| Wizard reports "PDO_MYSQL missing"   | Enable `pdo_mysql` in the server's `php.ini` and restart the Kangle PHP service |
| Attachment upload fails              | Check `api/uploads/` write permission and the `upload_max_filesize` / `post_max_size` config |
| Login lost after refresh             | Confirm the PHP session directory is writable; the Cookie domain matches the access domain; enabling HTTPS is recommended in production |
| Pages open but styles/images broken  | Confirm the `_nuxt`, `_fonts`, `api/uploads` paths are not being rewritten by the fallback rules |
| Wrong directory structure after extraction | Confirm you extracted the "no outer directory" package, so `index.html`, `api/`, `.htaccess` are directly in the root |

---

## 8. Production Recommendations

- **Enable HTTPS throughout**, and confirm the session config in the `security` section of `api/config.php` matches the site's protocol.
- Modify the `mail.from` and SMTP config in `api/config.php` to enable email notifications.
- Periodically export a data backup from the "Backup" page of the admin panel, and use the "Import" feature to restore it during migration.
- **Do not commit `api/config.php` to a public repository** (it is ignored via `.gitignore`) — it contains database credentials.

## 9. Updates & Upgrades

1. Rebuild and generate the latest deployment package (`./build-deploy.sh` or download via CI Artifacts).
2. Upload and overwrite the new package's content to the site root (**do not delete** `api/config.php`, `api/data/`, `api/uploads/`, to keep the configuration and data).
3. The framework automatically runs idempotent migrations on access (creates new tables/columns); no manual action is usually needed.
4. Verify that pages and historical data work correctly.

> Upgrading never overwrites existing database content; if you want to update the default body of the initial pages (homepage / grammar help), simply edit the corresponding page within the site.
